# Agent Board — 愿景与设计白皮书

[English](WHITEPAPER.md) | [简体中文](WHITEPAPER.zh-CN.md) | [返回 README](../README.zh-CN.md)

> **状态：长期设计方向，不是已经发布的协议规范。**
>
> Agent Board v0.2.3 是面向 AI 软件研发的本地任务账本与交付验收工作流。本文讨论更一般化的协作模型，**不代表当前已经实现 Goal 对象、分布式账本、跨节点身份体系或自动能力发现。**

## 一、为什么不止于任务看板

模型越来越强，上下文窗口越来越长，Agent 能够规划、执行并维护自己的记忆。但模型能力并不能自动回答：什么工作获得授权、具体交付了哪份成果、谁独立验证过、其他参与者凭什么接受它。

会话不能成为长期责任的唯一载体。Agent、模型和 Harness 都可能中断或更换，工作却仍然需要稳定的定义、交付证据和接受结论。

因此，除了管理 AI 开发任务，还值得探索一个更一般的问题：

**独立运行的智能体或节点，如何不依赖某一个参与者的记忆和判断，仍能可靠协作？**

我们尝试把协作语义从模型、执行环境、存储实现和部署形态中分离出来。

## 二、四个核心概念

**Goal 拥有账本，Task 承载契约，Delivery 携带证据，Governance 决定结果是否被接受。**

这是概念层的职责划分，不意味着当前 `aboard` 已经拥有全部对应的数据对象。

### Goal：目标与责任的归属

Goal 表示需要实现的结果，以及组织协作的边界。与 Goal 关联的账本记录其下的 Task、Delivery、证据和决策。

**账本在逻辑上属于 Goal**，不等于必须放在同一台服务器、一个全局数据库或某个中心调度者之下。一个节点既可以组织自己的 Goal，也可以承担其他 Goal 的 Task。

Goal 是长期概念层；v0.2.3 实现的是与本地 Git clone 关联的 Task 账本，并没有跨节点 Goal 账本。

### Task：可委托工作的契约

Task 定义一份能够独立交付的工作：目标结果、范围、约束、验收标准以及必要依赖。

它不需要管理 Agent 内部每个推理步骤或子任务。接收任务的节点负责自己的执行过程，并按契约交付。只有值得单独交接、验收和承担责任的工作，才有必要提升为独立 Task。

### Delivery：可识别的成果与证据

Delivery 需要说明**交付了什么、交付的是哪个版本、有什么证据支持**。

证据可能是代码、测试、文档、测量结果或其他领域材料。“已经完成”只是声明，不等于已经获得认可。

当前 AI 研发实现已通过结构化的 `baseline`、`fingerprint` 将验收结果绑定到可识别的交付。推广到其他领域时，证据格式和检查方法仍需分别验证。

### Governance：谁有权接受结果

Governance 规定谁可以授权执行、独立验证、要求返工、接受交付或决定例外。

**验证结论和接受裁决不同。** Verifier 的 `PASS` 与 Human 在没有 `PASS` 时明确接受一份成果，是两类不同事实。

治理并不天然意味着中心化管理机构，而是要求接受工作的规则明确、责任可追溯，不能由交付者自动宣布自己的成果有效。

## 三、节点、角色与协作形态

一个**节点**可以组织工作、执行工作，或者兼具两种能力。它可以负责自己的 Goal，同时作为专业参与者接受其他 Goal 的 Task。

Orchestrator、Worker、Verifier 是**具体协作中的职责角色**，不是对计算机、Agent 产品或组织机构的永久分类。

我们也不认为所有节点必须具备相同能力，更不把完全去中心化当作目标：

- 本地节点可以承担日常执行和用户交互。
- 专业节点可以提供特定领域能力、服务或独立验证。
- 大型云端及基础设施节点可能凭借算力、模型、资本和通用能力形成明显优势。

真正值得研究的，是如何让能力发现、履约证据、信誉和任务选择规则充分反映节点的专业差异，使不同层级的参与者都能找到合理的位置。

这不排斥中心化服务；本地部署、集中式组织和联合协作都可能合理。**去中心化是一种可选架构，不是必须坚持的理念。**

能力发现、信誉、采购和跨节点履约机制目前仍属于研究方向。

## 四、协议语义与产品实现分开

| 层次 | 负责什么 |
| --- | --- |
| 协作语义 | Goal、Task 契约、Delivery 证据、Governance 与接受规则 |
| Agent 执行环境 | 规划、调度、推理、工具、模型与会话 |
| 工程及领域规范 | 具体业务的质量要求和验证方法 |
| 本地参考实现 | 状态操作、Fact、持久化、CLI / MCP / Web |

长期协议不应绑定特定 Harness、模型、SQLite 表结构或 Git 工作流程；参考实现也不需要把调度、记忆和模型管理都装进核心账本。

现有 Aboard 的原则——**代码提供能力，Skill 定义规则，Board 保存事实**——是可继续沿用的工程边界。

## 五、可信协作的实际边界

记录了一个 Fact，并不代表该 Fact 自动真实。可靠协作还需要识别证据、保留来源、区分声明和独立检查、明确保存接受决策。

当前研发工作流已经实践了几项机制：

- Worker 留下稳定、可识别的交付。
- 新的独立 Verifier 根据验收标准形成 `PASS`、`RC` 或 `BLOCKED`。
- 返工形成新的交付；复用历史证据必须先判断其对当前交付是否仍然有效。
- Human 在没有 Verifier `PASS` 时的接受，单独记录为 `decision`。

但这些是**工作流规则**，并不是已经实现密码学保障的可信体系。当前来源标签属于自报告，Board 不认证 Agent 角色，本地 SQLite 也不是防篡改账本。

跨节点协作如要获得更强的可信度，仍必须研究身份、授权、证据完整性和争议处理。

## 六、当前能力与未来方向

| 当前 AI 研发实现 | 长期探索方向 |
| --- | --- |
| 本地 Task 与四种任务状态 | Goal 作为账本归属单位 |
| 结构化 Delivery、Verification、Decision 和 Handoff | 跨领域通用契约与证据 |
| 同一 Git clone 下 worktree 共享账本 | 跨节点交换、身份与信任 |
| Workflow Skill 的角色分工与验收规则 | 面向不同节点与领域的治理机制 |
| CLI、MCP、Web 接口 | 能力发现、联合协作与差异化节点 |

本文**不修改 v0.2.3 的接口、状态机或兼容性约定**。后续实现应从已出现的业务问题出发，先确认需求与验收标准，再决定是否需要扩充协议或基础设施。

## 七、继续研究的问题

1. 哪些事实必须跨 Agent、会话、模型或计算节点保存？
2. Task 的边界如何做到既便于执行，又能独立验收？
3. 怎样在不重复全部昂贵检查的前提下保证证据有效？
4. 一个节点凭什么信任另一个节点的证据，又由谁决定是否接受？
5. 不同能力和规模的节点怎样协作，而不被迫采用同一套执行技术栈？

我们的目标可以概括为：**让工作可以转移，让责任不会模糊。**
